# Rubric: is this reproduction package ready to post?

Every check below names a part of the package I can point at and a decision
rule someone else could apply to that same part and reach my answer. Each
check reads exactly one evidence source — the claim comment, the repo-facts
block, or the repro report — so a claim-only draft can still be graded on
the checks whose source exists. I grade the proof, never the formatting: a
terse report with a real artifact passes, and a long confident one with the
wrong artifact does not.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| `env-and-steps-rerunnable` | The repro report's environment record (the version, OS, and install method it names, plus any setting the issue itself treats as load-bearing: the driver, shell, browser language, build profile, config file) and its steps, read against the environment and trigger the issue states. | Fail if any of these hold. (a) The report names no environment at all — no version of the tool under test, or no OS/platform — so the attempt cannot be placed. A version alone with no platform is a fail only when the issue is platform-scoped; a version plus platform with no install method is NOT a failure. (b) The issue scopes the bug to a specific environment axis and the report is silent on that axis. Worked example: a Windows-only tunnel bug whose own steps read `minikube start --driver vmware`; a report that runs bare `minikube start` and records no OS, driver, or minikube version fails, because a stranger cannot tell what was even attempted. (c) The steps depend on an artifact the reader cannot obtain: a private repo, an unshared config, or an internal script, with no shareable substitute given. Worked example: "checked out our company monorepo (private; I cannot share it) and used our internal `.golangci.yml` (also not shareable)" fails — every step is gated behind something nobody else has. (d) The report ran a version materially different from the one the issue targets AND does not say so. Worked example: an issue confirmed by its reporter on the latest release and on main, against a report whose environment line reads `pandas 1.5.3` with no sentence acknowledging the gap, fails: the shown error is that old version's behavior, not evidence about the reported bug. Testing an older or newer version is NOT itself a failure. "The issue was filed against 13.0.0; behavior is unchanged on 15.2.0" and "the report is macOS + fish; shell and OS both differ, starship version matches" both PASS — stating the delta is the pass, hiding it is the fail. Reproducing on a different OS or install method than the reporter, with that difference named, is NOT a failure. Not having every knob the issue mentions (for example, no way to force a smaller limit from the CLI) is NOT a step failure when the report says so. | required |
| `artifact-shows-issue-behavior` | The report's artifacts — command output, log excerpt, transcript, described screenshot — read line by line against the behavior the issue states: its error text, exit code, symptom, and the exact invocation or syntax that triggers it. Read the artifact only; ignore every sentence of narration around it. | Fail if any of these hold. (a) The command, expression, or input in the artifact is not the one the issue names as the trigger, so the artifact tests something else. Worked example: an issue that triggers on the offset-from-end range syntax `--line-range ':-18446744073709551614'`, against an artifact running `--line-range '18446744073709551614:'` (a prefix range), fails however many times it was repeated. Worked example: an issue about `Invalid path expression` from `path({} as {$a} | .)`, against an artifact whose expression was altered to `path({} as {$b} | $b)` and produced `$b is not defined ... 1 compile error`, fails — a compile error is not the reported runtime behavior. (b) The artifact shows a different failure mode than the issue describes: a graceful validation error with exit 1 where the issue reports a panic or abort with exit 101, or output still scrolling with the process alive where the issue reports a crash. Worked example: an issue reporting the terminal process crashing, against an artifact reporting "pages of raw escape-sequence text ... the window remained open afterward and the prompt returned", fails no matter how polished the report around it. (c) The artifact shows only that the tool is installed, running, or set up, not the reported symptom. Worked example: a `--version` banner plus a session list plus "all three tabs visible" fails on an issue whose symptom is one blank, input-ignoring pane — nothing shown is a blank pane, a dump-screen result, or the stalled log. (d) There is no artifact at all: the report asserts the behavior in prose ("can 100% confirm", "it totally overflows just like the screenshots show", "I verified this race condition") with no output, transcript, measurement, or recording of its own. An artifact produced by a CANNOT-REPRODUCE attempt is NOT a failure here; `outcome-matches-evidence` is the check that reads it. Confidence markers — "thoroughly", "ran it 10 times", "on two separate machines", "guaranteed reproducible" — are never evidence and never rescue an artifact that fails (a) through (d). | required |
| `outcome-matches-evidence` | The report's stated result (its "Actual", conclusion, or summary line) and the claim comment's confidence, read against what the report's own artifacts actually show. | Pass when the words claim no more than the artifacts show. A report that states it could NOT reproduce PASSES this check, and is a genuine reproduction package, when all of these hold: the negative result is stated plainly and up front rather than buried; the attempt is real and shown, meaning there is an artifact of what DID happen and not just an assertion that nothing happened; and the report names what differed from the issue's conditions as a mechanism rather than a shrug. Worked example, PASS: "Result: I could NOT reproduce scenario 2 ... in every run, all ONE batches were written before any TWO batch ... fd appears to flush both command buffers at the same file-count boundary on this input (uniform name lengths); a distribution where argument lengths differ per file, or a much lower forced limit than my 2 MiB ARG_MAX, may be required" — negative result up front, marker-order artifact, named delta, named mechanism. Worked example, PASS: "cannot reproduce on Linux + zsh with the report's exact layout and config ... the module renders on every attempt ... my prompt shows the resolved physical path, which suggests my shell reports PWD differently for symlinked directories than fish does on macOS." Fail if any of these hold. (a) The report states a positive reproduction while its own artifact shows something else, or states an "Expected" that contradicts what it shows. Worked example: "Expected: one of the three panes comes up blank ... Actual: the session starts and the tabs are all present ... This confirms the bug report's scenario is reproducible" fails — the stated actual is not the issue's symptom and the expected is written backwards from what was shown. (b) The report asserts a root cause, mechanism, or diagnosis it did not demonstrate. Worked example: "The problem is a race condition between the debounced save and the note-switch handler ... I verified this race condition is the cause", with no transcript, no instrumentation, and no artifact, fails. (c) The claim comment claims a reproduction the report does not support, or claims a certainty the report's evidence does not carry. A claim comment reading "I tried to reproduce it before claiming and so far cannot (details below)" alongside a cannot-reproduce report is a MATCH and passes. Proposing a hypothesis explicitly labelled as one — "which suggests", "may be required", "looks necessary" — is NOT an overclaim. | required |
| `claim-comment-specific-and-honest` | The candidate claim comment alone, read against the issue's title, body, and thread. Do not use the repro report to repair it: a stranger reads the claim comment as posted. | Fail if any of these hold. (a) The comment contains nothing that could only have been written about this issue — no reference to the specific symptom, file, version, syntax, or thread comment at stake. A comment that would read identically under any other issue in any other repo fails. (b) It promises a fix on a schedule, or with a guarantee, that the author cannot honor. Worked example: "Kindly assign it to me, I will fix it within 2 days guaranteed ... please check it and keep this issue reserved for me" fails — an outsider can neither reserve an issue nor guarantee a landing date. (c) It self-assigns or declares ownership in place of stating an intent. Worked example: "Assigning myself to this, I know exactly what the reporter is talking about" fails. (d) It is a bare +1, me-too, or bump with no stated intent to work. Worked example: "+1 also seeing this!! any updates on a fix?? would love for this to get resolved soon" fails. (e) It asserts a completed understanding of internals the package does not evidence, for example "I have completed a full reproduction and analysis and I understand the compiler internals involved". A concrete, falsifiable next step is the shape that passes: "my next step is reading how the translator loads locale files relative to when FES fires", or "I'll verify whether the vendored go-yaml carries the fix from yaml/go-yaml#357". Enthusiasm, greetings, thanking the maintainers, or simply being short are NOT failures on their own; a two-sentence claim naming the version reproduced and one next step passes. Asking to be assigned is NOT a failure when it accompanies specific evidence and a real next step; it fails only in combination with (a), (b), or (e). | required |
| `ai-disclosure-when-policy-requires` | The `- contribution policy` line in the repo-facts block, read for its modal verb and its stated scope, together with the candidate claim comment and repro report. Treat every course package as AI-assisted work: the question is never whether AI was used, only whether this repo's stated policy obliges the author to say so in THIS artifact. | Decide by the policy line, in this order. (1) If the policy line does not mention AI at all ("standard contribution guide; no stated AI policy"), this check PASSES regardless of whether the package discloses. Disclosure is neither required nor rewarded here: do not fail a silent package, and do not fail a disclosing one. (2) If the policy permits AI with conditions — welcome with a human in the loop, assistive use allowed, you are responsible for what you submit, understand and test what you send, low-quality AI content is closed — this check PASSES whether or not the package discloses, because the policy states terms of use, not a notification duty. Both directions pass: a package that writes "Per the AI usage policy: I used an AI assistant to help me organize this report; I ran and verified every step myself" passes, and a package under "generative AI tools welcome; you are responsible for all contributions" that says nothing about AI also passes. (3) If the policy requires disclosure but scopes that requirement to a part of the workflow this package is not — most often pull requests — this check PASSES with no disclosure. THIS IS THE CASE MOST EASILY GRADED WRONG: read the scope clause, not the keywords. Worked example, PASS with no disclosure anywhere in the package: "AI-assisted code contributions ... must state the tool and the extent of its use IN THE PULL REQUEST; comments to maintainers are expected to be in the contributor's own words (AI help with grammar, spelling, and proofreading is fine); the policy states no disclosure ask for issue comments" — the package is a claim comment and a repro report, not a pull request, so nothing is owed. A policy that restricts who may WRITE comments without requiring disclosure is likewise not a disclosure requirement: "comments to maintainers must be written by humans in their own words, and AI-generated comments may be hidden" PASSES when the comment reads as a person's own words about this specific issue. (4) FAIL only when the policy states a disclosure duty in mandatory terms whose scope covers what this package posts — comments, issues, or contributions "in any form" — and neither the claim comment nor the repro report names AI assistance. Worked example, FAIL: "All AI usage in any form must be disclosed, stating the tool used and the extent of the assistance; AI-assisted issues and comments must be reviewed and edited by a human before submission", against a package whose two comments never mention a tool. A package that fails here fails even when every proof check is flawless: posting under a disclosure rule without disclosing is the harm, and it is independent of the quality of the reproduction. | required |
| `control-or-contrast-run` | The report's artifacts, looking for a second run alongside the failing one: the same command with the trigger removed, a known-good input, or the working case the issue contrasts against. | Prefer a report that shows the boundary as well as the failure — the flag dropped and the output correct, English-first instead of Japanese-first, a zero-header control next to the one-header failure. A control run turns "it failed for me" into "this is what makes it fail", which is the fastest thing a maintainer can act on. Never changes a verdict: a single-run report whose artifact plainly shows the issue's behavior is complete, and plenty of issues have no meaningful control to run. | preferred |
| `concrete-next-step` | The claim comment's closing, read for a named file, module, function, pull request, or question it intends to pursue. | Prefer a claim that names where it will look next: a specific printer, a specific function like `Index.set_names` or `contract_repo_path`, the exceptions path that emits a named error, or testing the draft patch already in the thread. It shows the author read the thread, and it gives the maintainer something concrete to redirect. Never changes a verdict: a correct, honest package whose claim ends at "I'd like to work on this" is still ready to post. | preferred |

## Verdict rule

`accept` if and only if every `required` check grades `pass`. A single
`required` fail produces `reject`, and the read-out names the check that
sank it. There is no partial credit and no averaging: these five checks are
five independent ways for a package to waste a maintainer's time, and one
of them is enough.

`unclear` on a required check counts as `fail`. A reproduction whose
environment, artifact, honesty, claim wording, or disclosure obligation I
cannot establish from the package in front of me is not a proof a stranger
can act on. One exception: evidence that is present and explicitly negative
is evidence of absence, not absent evidence, and grades `pass`. That covers
`no stated AI policy` on the contribution-policy line, a report that states
plainly that it could not reproduce and shows the attempt, and a report
that names a knob it looked for and could not find.

`preferred` checks never change a verdict. Grade them and report them; they
say how strong an accepted package is, not whether it is accepted.

Claim-only drafts, in live mode before the repro report exists, grade only
the checks whose evidence is the claim comment or the repo-facts block:
`claim-comment-specific-and-honest` and `ai-disclosure-when-policy-requires`,
reading the disclosure duty against the claim comment alone. Grade
`env-and-steps-rerunnable`, `artifact-shows-issue-behavior`,
`outcome-matches-evidence`, and `control-or-contrast-run` as `unclear` with
evidence `not yet applicable: claim-only draft`, and leave them out of the
verdict rule. Those `unclear` grades do NOT count as fails. This carve-out
is for a draft written before any reproduction was attempted; it never
extends to a full package that simply omitted its report. The verdict then
answers only the narrower question: is this claim comment ready to post?
